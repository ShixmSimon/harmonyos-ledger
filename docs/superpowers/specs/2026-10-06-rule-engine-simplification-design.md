# OCR 与通知识别规则引擎精简设计

状态：待用户评审

日期：2026-10-06

## 目标与约束

用户希望减少规则配置和正则维护负担，同时保留识别能力。OCR 必须允许用户在应用内新增来源和常见账单版式，不能把解析入口限定为当前的账单列表和工商银行流水。通知规则可以简化配置方式。

本次设计遵守以下约束：

- 保留微信、支付宝、工商银行和中信银行的现有默认识别行为。
- 保留本地已保存的自定义规则和顺序；规则配置迁移失败时明确报错，不以默认规则覆盖。
- OCR 新来源使用账目已有的字符串来源字段，不修改账本数据库结构。
- 保留日期可信度、退款/失败保护、来源歧义交由用户选择、入账前复核等既有约束。
- 不接入远程 AI 服务，不上传 OCR 文字、截图或通知正文。本设计只简化规则接口，使外部 AI 生成的规则更容易录入。

## 当前复杂度

- OCR 来源类型目前固定为 `wechat`、`alipay`、`icbc`，解析入口按 `receipt-list` 与 `icbc-statement` 两个枚举分派。
- OCR 编辑器要求用户维护加权来源正则、分数阈值、分差、多个字段正则及各自的捕获组编号。
- 通知规则把正文正则与金额、方向、日期、商户、分类捕获组编号绑定；改动一个捕获组可能令后续编号全部变化。
- 分类映射、商户前缀、备注模板和失败/退款/汇总过滤等内部选项也都出现在编辑流程中。
- 两类 OCR 布局确实有不同的数据组织方式，不能靠删除布局差异来简化；应由通用的记录分组和字段抽取能力表达。

## 方案比较

### 方案 A：只折叠高级配置

保留当前规则模型和解析器，只调整编辑器默认显示。

优点是风险和改动量最低。缺点是 OCR 来源与布局仍然固定，捕获组编号仍是规则格式的一部分，AI 生成配置仍需要理解全部内部字段。

### 方案 B：通用 OCR 规则解释器，并精简通知规则

把 OCR 来源、记录分组、字段提取表达为可保存的规则数据；内置来源成为默认规则，新来源和可表达的新布局可以在应用内配置。通知正文用语义捕获字段代替数字组号，并保留旧规则兼容。

这能满足应用内扩展 OCR 的要求，也能显著减少新通知规则的配置项。代价是需要建立稳定的通用解析原语、迁移 Preferences 规则格式，并为旧规则保留兼容读取路径。

### 方案 C：保留解析器注册表

增加更多代码内置布局策略，每条规则只选择已有策略。

这种方式可针对已知格式精调解析，但新布局需要更新应用，不满足用户选择的“应用内配置”。

**选择方案 B。** OCR 的新布局只要能由通用记录分组和字段提取原语表达，就能无需发版而新增；完全不同的视觉/语义结构若超出这些原语，仍需先扩展引擎能力。

## 设计

### OCR 规则

1. 来源标识改为动态字符串，并同时保存用于规则页和草稿展示的来源名称。来源匹配表达式在应用内编辑，去掉每条表达式的权重；分数按命中的表达式数量计算。自动识别选唯一最高分来源，平分或零命中时要求用户选择，不暴露最低分和分差配置。
2. 移除按来源硬编码的 `layoutStrategy` 分支。通用解析器先依据 OCR 行的坐标聚合视觉行，再按规则配置把行组成交易记录：
   - 视觉行模式：每个聚合行形成候选记录，适合普通交易列表和表格。
   - 起始锚点模式：匹配配置的交易起始行，并将后续行组合到下一条记录开始处，适合多行交易块。
   - 可选的列范围限制允许在表格中按 OCR 行的横向位置提取字段。
3. 日期、金额、时间、方向、商户和分类分别配置字段表达式。每个表达式固定使用第一个捕获组作为值，结构分组必须使用非捕获组，编辑器不再要求用户输入组编号。
4. 方向关键词、失败/退款过滤、汇总排除、默认分类及分类映射继续受规则控制；高级过滤配置可折叠，常用来源规则提供经过验证的默认值。
5. 微信和支付宝默认规则使用视觉行模式。当前工商银行专用解析行为先保留为兼容适配器，并逐步用通用记录模式表达；它不能成为新规则唯一可选的布局。
6. `OcrSourceDetector` 返回匹配规则/动态来源，而不是只返回固定 `ImportSource` 联合类型。人工来源选择仍只在所选来源内试规则。来源展示使用规则中的显示名称，不对未知来源回退显示“工商银行”。

### 通知规则

1. 新规则的正文正则使用语义命名捕获：必需的 `amount` 与 `direction`，可选的 `date`、`merchant` 和 `category`。引擎根据命名字段取值，用户不再维护 `amountGroup`、`directionGroup` 等编号。
2. 收入/支出关键词继续明确配置，用来校验并分类 `direction` 捕获值。缺少方向或金额时不入账；每个内置来源现有的失败、撤销、取消和退款拦截行为保持不变，不额外改变自定义规则的匹配语义。
3. 日期策略、默认商户、默认分类和来源保留。商户前缀、分类映射和备注模板作为可选高级配置，不要求新规则填写。
4. 来源关键词仍支持自定义来源应用。规则顺序、首个匹配规则拥有通知的行为保持不变。

### 旧规则与本地存储

1. OCR 与通知 Preferences 规则集升级到新版本格式。
2. 旧版 OCR 规则保留原正则、来源匹配和顺序；可无损映射的项目转为通用规则。原工商银行专用解析器在兼容期内继续处理未能直接转译的已存规则。
3. 旧版通知规则保留原正文正则和捕获组映射，在新版本格式中作为兼容规则读取。新建规则使用命名捕获格式；不能确认语义等价时不自动重写用户正则。
4. 迁移应幂等；只在完整解码并验证通过后写入新版本。空规则集仍保持为空，损坏或未知版本继续显式报错，不静默恢复默认值。
5. 账本数据库 schema 不变；规则更改只影响之后的 OCR 导入与通知处理，不重解析历史内容。

## 影响范围

- OCR：规则类型、验证与存储、来源检测、导入协调器、记录分组与字段抽取、规则编辑器和 OCR 测试。
- 通知：规则类型、正文匹配与验证、规则存储迁移、通知规则编辑器和通知测试。
- 文档：更新 OCR/通知规则说明与架构数据流。
- 不改账本数据库表，不新增外部依赖，不增加网络调用。

## 验收与验证

1. 旧版本 Preferences 样例可以迁移并保留规则内容、顺序、启用状态和解析行为；重复加载不重复迁移。
2. 用户能在规则页新增一个非内置来源，并为至少两种通用布局配置来源和字段规则；规则无效时不入账，来源歧义仍要求人工选择。
3. 当前微信、支付宝、工商银行截图解析行为及日期、金额、退款、失败、汇总过滤回归通过；用户确认仍是 OCR 入账的最终门槛。
4. 新通知规则用命名字段匹配收入和支出，日期/商户字段可缺省；旧版通知规则仍可解析，错误捕获字段不会自动入账。
5. Node 规则测试通过，HAP 构建通过；在可用的 HarmonyOS 7 / API 26 真机核对新建 OCR 规则、手动来源选择、通知规则编辑及解析流程。
6. 交付前运行 `git diff --check`。

## 风险与边界

- 通用分组和字段正则不能理解任意视觉设计。规则可组合的能力由记录分组、字段范围和邻接关系这些原语限定；超出原语的版式需要先扩展引擎，不能承诺任意截图全自动适配。
- OCR 结果和通知模板会随应用版本变化。新规则必须用真实样例及反例验证；不可靠日期、方向或金额继续要求跳过或人工复核。
- HarmonyOS 运行时对命名正则捕获的支持需通过项目构建和 API 26 设备验证；若类型或运行时限制不兼容，实施阶段应采用等价的安全适配层，而不恢复让用户维护数字组号的编辑体验。
- 迁移逻辑若遇到无法安全转换的自定义规则，应保留兼容表示并报告状态，不能猜测、删除或覆盖。
